## The one idea that matters: builds, not version strings

spec-kitty does not yet report version + build together. During pre-release QA the version
string identifies nothing — `main` declared `4.0.0rc4` for days with no rc4 tag and no PyPI
artifact, so "wait for rc4 on PyPI" would have blocked indefinitely. Resolve a wanted
version to a **commit**, pin the full SHA, and report what was installed by SHA.

```bash
git ls-remote --tags https://github.com/spec-kitty/spec-kitty.git   # tagged builds
git ls-remote https://github.com/spec-kitty/spec-kitty.git HEAD     # main HEAD
gh api repos/spec-kitty/spec-kitty/contents/pyproject.toml --jq '.content' | base64 -d | grep -E '^version'
```

Build IDs in play: 3.2.7 = `fb4e8fa98` · rc3 = `fbe1109fa` · rc4 candidate = `619bd1137` ·
**rc4 released = `5309c4107`** · **rc5 dev (installed) = `d57619a90`**.

## Traps that cost time here

**`spec-kitty upgrade`'s exit code is not a health signal.** It returns 1 while printing
`Project is already up to date!` — verified on `d57619a90` with a clean tree, `current ==
target`, no prompt and no errors. Check convergence with `pending_migrations: []` and
`doctor tool-surfaces` exit 0 instead. Filing as Action 2 (#992, persistence vs closed #4775).

**`upgrade --dry-run` claims 184 outstanding repairs on a converged project.** `doctor
tool-surfaces` simultaneously reports clean. The dry-run cannot answer "does this need
upgrading?". Filing as Action 3 (#994, persistence vs closed #4777).

**The RELEASED rc4 cannot run `upgrade` on Windows at all** — `NotImplementedError: utime:
follow_symlinks unavailable on this platform` at `skills/installer.py:980`. Dormant in
`619bd1137`, exposed in `5309c4107`, dormant again in `d57619a90` — the call is present in all
three, only reachability changed. Do not assume a newer build fixed it. Filing as Action 1 (#1005).

**`.kittify/migrations/` is gitignored (#996).** The mission-state run manifest and the
quarantined rows live only in the working tree; `git clean -xfd` destroys them. Copies are in
the out-of-tree backup. Still true on `d57619a90`.

**`docs/temp/` is gitignored** (`.gitignore:35`, `temp/`). A findings copy sits there for a bot
running against this working tree, but it will never push. Any agent reading from a clone,
office2, or the QA Windows account must read the canonical
`docs/diagnostics/spec-kitty-4.0.0rc4-upgrade-findings.md`.

**`.kittify/` and `kitty-specs/` are spec-kitty-owned.** When merge conflicts hit generated
manifests, do not hand-resolve — take either side to clear the tree, then re-run
`spec-kitty upgrade` so the CLI regenerates them authoritatively (that is how `331d46fd` was
produced).

**Two of our root causes were wrong.** #993's three-run convergence was not the
`_recheck_command_completion` `installed_at` race we blamed; upstream found a Windows POSIX-mode
assertion at the same gate. #994's phantom count may likewise not be the `chmod` theory — the
fix that theory predicted landed and the count did not move. A mechanism that fits the evidence
is not necessarily the mechanism.
