## Decision: 4 OpenClaw agents, not 5

**Decision:** The mission treats the set of registered OpenClaw agents as `felix-admin-capture`, `felix-admin-escalation`, `felix-admin-habits`, `felix-admin-tasker`, plus the `main/` and `main-patches/` support directories under `scripts/openclaw/agents/`. Six directories total; four of them are proper agents.

**Rationale:** Direct audit of `scripts/openclaw/agents/` on 2026-04-11 showed only these directories. The spec.md's initial "5 agents" figure was an estimate that did not match the ground truth.

**Alternatives considered:**
- Assume the issue body's "5 agents" count and plan accordingly → rejected because it does not match the repository state.
- Cross-reference `docs/constitution/AGENT-REGISTRY.md` → deferred to WP01 as a sanity check step; the registry may have additional agents not yet deployed, which would be a separate concern.

**Implication:** The work package file coverage targets four agents. Spec.md updated to reflect the correction.

## Decision: `ai-agents/` directory is in migration scope

**Decision:** `ai-agents/claude-instructions.md` and `ai-agents/claude-code-instructions.md` are in scope for the WP02 migration. They are converted to `.tmpl` sources with `{{VAULT_*}}` markers alongside the OpenClaw agent files.

**Rationale:** Grep audit of the repo on 2026-04-11 returned hits in both files for vault folder literals. They are not OpenClaw agents but they are Claude instruction files that direct Claude Code behavior against the vault, and they suffer the same drift-risk as any hardcoded reference. The spec's FR-002 states every production file except the `_private/` boundary must use markers — these files qualify.

**Alternatives considered:**
- Treat `ai-agents/` as out of scope because it's for Claude, not OpenClaw → rejected because the FR-002 criterion is file-type-agnostic.
- Put `ai-agents/` in a separate mission → rejected because the cost of migrating two files alongside the OpenClaw work is trivial, and coherence benefits from a single sweep.

**Implication:** WP02 adds two entries to `targets.json` for the Claude instruction files. Spec.md updated to mention `ai-agents/` explicitly.

## Decision: Charter files (`.kittify/charter/*`) handled via `spec-kitty charter sync`, not direct edit

**Decision:** Vault-path references in `.kittify/charter/charter.md`, `.kittify/charter/directives.yaml`, and `.kittify/charter/library/user-project-profile.md` are handled through the spec-kitty charter workflow (`spec-kitty charter sync`), not through direct edits. The planning phase identified these files as containing vault path hits, but `.kittify/` is workflow-managed per the project rules.

**Rationale:**
- CLAUDE.md explicitly states: *"`.kittify/` are owned by spec-kitty. These directories contain ... workflow configuration managed exclusively by spec-kitty commands. Agents and humans must never directly create, edit, move, or delete files in these directories."*
- The charter source of truth is `charter.md`; `directives.yaml` and the `library/` files are regenerated by `spec-kitty charter sync`.
- If `charter.md` contains hardcoded vault paths that are NOT the `_private/` boundary, they should be edited in place (operator-driven, not agent-driven) and then `spec-kitty charter sync` runs to propagate.
- If the only hardcoded reference is the `_private/` boundary, no charter edit is required — it stays as-is per C-001.

**Alternatives considered:**
- Add `.kittify/charter/charter.md` to `targets.json` as a `.tmpl` source → rejected because spec-kitty's sync mechanism is not the same as the `scripts/vault/deploy.py` template substitution, and mixing the two would break the charter workflow.
- Skip charter files entirely → rejected because if non-boundary references exist there, they are real drift-risk surfaces.

**Implication:** WP02 includes an audit step: check `charter.md` for non-`_private/` vault references. If any exist, operator updates `charter.md` manually and runs `spec-kitty charter sync`. If none exist, charter files are out of the migration sweep (the `_private/` line stays hardcoded per C-001).

## Decision: Mission 026 adds `scripts/deploy/deploy-f026.sh` wrapper (charter compliance via option B)

**Decision:** Mission 026 creates `scripts/deploy/deploy-f026.sh` as a thin wrapper around `python3 scripts/vault/deploy.py --apply`. The wrapper handles mission-specific orchestration: cron pause, deploy invocation, verification checks, smoke tests, cron resume.

**Rationale:**
- The charter rule states: *"Every feature that deploys code, agents, skills, or scheduled services to office2 must include a deploy script at `scripts/deploy/deploy-f{NNN}.sh`."*
- Mission 024 built `scripts/vault/deploy.py` as a shared primitive but did not produce `deploy-f024.sh`. Whether this was a rule violation or an unspoken exception is unclear.
- The safest path for mission 026 is to comply with the literal rule: ship a `deploy-f026.sh`. The wrapper has real value beyond glue code — it encapsulates the cron pause/resume sequence and the verification orchestration, which need to be scripted anyway per FR-4 and FR-5.
- Operator decision Q2 (Q2 of planning interrogation) selected option B (add the wrapper) over option A (no wrapper, use `deploy.py` directly).

**Alternatives considered:**
- Option A: no wrapper, use `scripts/vault/deploy.py` directly → rejected by operator on Q2.
- Option C: add `deploy-f026.sh` AND retroactively add `deploy-f024.sh` → rejected as scope creep on a finished mission.
- Option D: amend the charter rule to recognize shared deploy primitives → captured as a separate follow-up, see below.

**Implication:** WP01 creates `scripts/deploy/deploy-f026.sh` per the contract in `contracts/deploy-wrapper-contract.md`. The wrapper is a one-shot script tied to this mission and not intended for reuse beyond the verification phase.

## Decision: Charter rule drift captured as separate issue #154

**Decision:** The charter-rule drift (rule says `deploy-f{NNN}.sh` required; mission 024 used `scripts/vault/deploy.py` directly without a wrapper) is captured as [kentonium3/kg-automation#154](https://github.com/kentonium3/kg-automation/issues/154) as a charter amendment proposal. Mission 026 proceeds with option B compliance and does not block on #154 resolution.

**Rationale:**
- The drift indicates the rule may not reflect current infrastructure reality (shared deploy primitives didn't exist when the rule was written).
- A proper amendment ("either `deploy-f{NNN}.sh` OR document which shared primitive is used") captures the intent (every deploy is named and documented) while recognizing that some deploys share infrastructure.
- This is a charter-level change and should go through its own deliberation, not be bundled into mission 026's infrastructure refactor.

**Alternatives considered:**
- Ignore the drift → rejected because it would silently normalize non-compliance.
- Force mission 026 to retroactively fix mission 024 → rejected as scope creep.

**Implication:** Filed as P2-infra / area/docs / spec: brief. Does not block this mission.

## Decision: Smoke test scope is `felix-admin-capture` + `felix-admin-tasker`

**Decision:** Post-rename smoke tests (FR-005, WP05 step 9–10) cover `felix-admin-capture` and `felix-admin-tasker`, both with full end-to-end invocations. Other agents are covered by the repo-wide grep check (NFR-002) and the unreplaced-marker check (NFR-003) only.

**Rationale:**
- Operator decision Q3 of planning interrogation.
- `felix-admin-capture` is the most affected by the inbox rename (runs 4× per day against that folder).
- `felix-admin-tasker` is the second-highest-traffic agent touching vault paths.
- Grep checks catch the vast majority of failure modes (unreplaced markers, stale literals) cheaply. Two full invocations catch runtime issues grep can't.
- Testing all four agents end-to-end would require fixture engineering and token cost without proportional benefit — the other two will fire on their own cron schedules soon after the migration.

**Alternatives considered:**
- Only smoke-test `felix-admin-capture` → rejected as insufficient coverage.
- Smoke-test all four agents → rejected as disproportionate cost.
- Shallow "health check" mode for all four → rejected because not all agents have a dry-run mode and building one is scope creep.

**Implication:** `deploy-f026.sh` wrapper invokes both agents in sequence before re-enabling the cron. Each invocation has explicit pass/fail criteria (agent exits 0, produces expected log lines, does not write to unexpected paths).

## Decision: Cron pause during risky window (option A from specify Q3)

**Decision:** The `felix-admin-capture` cron is paused on office2 before WP05 step 3 (folder creation) and re-enabled in WP05 step 12 (after verification passes). During the pause window, no inbox processing occurs.

**Rationale:**
- Operator decision (discovery Q3 in specify phase).
- The inbox typically has 0–1 unprocessed items per run, so a 15–90 minute pause window has negligible practical impact.
- A pause is simpler and safer than designing for cron-safe incremental deploys (which would require every intermediate state to be a valid runtime state — significant engineering cost for a one-time migration).
- Aligns with the constitutional "never silent failures" directive — a pause is explicit and auditable.

**Alternatives considered:**
- Design for cron-safe incremental deploys → rejected as over-engineered.
- Accept the risk without pausing → rejected as too fragile.

**Implication:** `deploy-f026.sh` includes pause and resume logic. The pause mechanism itself is tested in WP04 (ensure the pause command actually works) before WP05 depends on it.

## Decision: Six phase-aligned work packages (option B from Q4)

**Decision:** Mission is decomposed into six work packages (WP01–WP06) aligned with execution phases: registry extension, code migration, doc sync, pre-rename deploy + fidelity checkpoint, rename + post-rename deploy + smoke tests, cross-repo + close-out.

**Rationale:**
- Operator decision Q4 of planning interrogation.
- Six WPs strike a balance between granular review and execution coherence. Each WP is a self-contained operational phase with clear entry/exit gates.
- WP04 is dedicated specifically to proving refactor fidelity (DIRECTIVE_034 test-first checkpoint). Separating it from WP05 forces an explicit gate between "we refactored" and "we changed runtime state."
- WP05 is the risky window and has an explicit operator review gate at entry.

**Alternatives considered:**
- Option A: 10–12 small WPs (one per FR or per agent) → rejected as high overhead.
- Option C: 3–4 minimal WPs → rejected because WP01 would become too large.

**Implication:** `/spec-kitty.tasks` will generate WP01–WP06 files. Sequential dependency: WP01 → WP02 → WP03 → WP04 → WP05 → WP06. WP02 and WP03 may be committed separately but WP03 gates on WP02 for doc accuracy (doc sync references the new markers). True parallelism is limited.

## Decision: Tier 2 change-risk classification with Restic pre-flight

**Decision:** This mission is Tier 2 under the change-risk taxonomy. Restic backup verification is required before WP05 entry; if no backup exists within 24 hours, a new backup is triggered first.

**Rationale:**
- The mission modifies application state on office2 (deployed agent files) and vault folder structure (top-level directory renames). Both qualify as Tier 2 (Application/State) per `docs/design/architecture/data/change-risk-taxonomy.json`.
- The existing Tier 2 pre-flight checklist in `docs/runbooks/governance/pre-flight-checklist.md` and post-change verification in `docs/runbooks/governance/post-change-verification.md` apply directly.
- Restic restore is the rollback-of-last-resort if WP05 corrupts vault state beyond manual recovery.

**Alternatives considered:**
- Classify as Tier 3 (Standard) and skip backup verification → rejected because top-level folder renames can cascade to wikilink breakage if the Obsidian assumption is wrong.
- Classify as Tier 1 and add full connectivity verification → rejected as overkill; the mission does not change network topology.

**Implication:** WP05 step 1 is "Tier 2 backup verification" — operator confirms Restic backup is ≤24h old or triggers one.
