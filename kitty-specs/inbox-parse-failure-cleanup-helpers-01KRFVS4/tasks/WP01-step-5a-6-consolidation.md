# WP01 — Implement Step 5a + Step 6 consolidation helpers

## Objective

Add two new orchestrator scripts in `scripts/inbox/` that consolidate the deterministic loops currently inlined in the felix-admin-capture AGENTS.md prompt (Step 5a's strip loop and Step 6's file-issue-then-inject-per-entry sequence), and update both `AGENTS.md` and `AGENTS.md.tmpl` so each step becomes a single command invocation.

**Review scope (WP01)**: T001–T007 — two new helpers + two new test files + AGENTS.md and AGENTS.md.tmpl edits + local pytest pass. Deploy and end-to-end SC-003 canary verification are split out as **Post-Merge Operator Verification** below (same scoping discipline as the merged #254 — commit b82aac4).

## Context

GitHub issue #253 documents felix-admin-capture (haiku 4.5) skipping Step 6.2 (marker injection) while fabricating a "script not found" explanation during the mission #185 canary on 2026-05-12. Root cause: multi-step bash recipes inside an LLM prompt are fragile to model variance. Step 5a has the same shape and the same latent fragility. This WP applies the deterministic-work-into-scripts principle: factor each multi-step deterministic loop into a Python helper, then make the prompt one command per step.

See [spec.md](../spec.md), [plan.md](../plan.md), [research.md](../research.md), and [quickstart.md](../quickstart.md) for full context.

The underlying scripts (`file_inbox_quality_issue.py`, `inject_parse_error_marker.py`, `strip_parse_error_marker.py`) already expose clean library APIs — the new orchestrators import them directly (plan Phase 0 Decision 1). The existing CLI surfaces are preserved unchanged for standalone debug use.

### T001 — Create `scripts/inbox/handle_parse_failures.py`

**Purpose**: Single helper that does Step 6 end-to-end — file/dedup the inbox-quality issue, then inject parse-error markers for every entry.

**CLI**:

```
python3 handle_parse_failures.py @/path/to/prescan.json [--date YYYY-MM-DD]
```

**Steps**:

1. Argument parsing:
   - Positional: a single string. If it starts with `@`, treat the remainder as a path to a JSON file. Read and parse. Otherwise, treat the string itself as the JSON path (`@` is optional for caller convenience, but agent will pass `@<path>`).
   - `--date`: optional ISO date (`YYYY-MM-DD`). Default: today in UTC. Used for the marker line.
2. From the parsed JSON, extract `parse_failures` (default `[]` if missing).
3. If the list is empty: exit 0 immediately, emit nothing.
4. Otherwise:
   a. Call `file_inbox_quality_issue.find_existing_open_issue()`. If it returns an int, that's the issue number; emit a `log_action.py` subprocess call with `--action inbox_quality_issue_deduped --context '{"issue_number": <N>, "parse_failure_count": <len>}'`.
   b. Else call `file_inbox_quality_issue.file_new_issue(parse_failures, date_str)` — get the new issue number; emit a `log_action.py` subprocess call with `--action inbox_quality_issue_filed --context '{"issue_number": <N>, "parse_failure_count": <len>}'`.
   c. For each entry in `parse_failures`:
      - Call `inject_parse_error_marker.inject_marker(Path(entry["path"]), issue_number, date_str)`.
      - On success (True/no-raise): emit a `log_action.py` subprocess call with `--action parse_error_marker_injected --context '{"source_file": "<path>", "issue_number": <N>, "reason": "<entry.reason or "">"}'`.
      - On failure (False or raise): emit a `log_action.py` subprocess call with `--action parse_failure_handling_error --context '{"source_file": "<path>", "issue_number": <N>, "error": "<exception str>"}'`. Capture this failure in a local counter and continue to the next entry.
5. Print the issue number to stdout (single line, no trailing whitespace beyond the newline that `print` adds).
6. Exit 0 if no failures, else 1. On non-zero exit, print to stderr a summary of failed paths.

**Imports** (the library-style functions that already exist):

```python
from inject_parse_error_marker import inject_marker
from file_inbox_quality_issue import find_existing_open_issue, file_new_issue
```

Match the import style used by `tests/inbox/conftest.py` if it manipulates `sys.path`. Inspect `tests/inbox/conftest.py` and `scripts/inbox/file_inbox_quality_issue.py` to confirm the pattern before deciding between `from X import Y` and `from scripts.inbox.X import Y`.

**`log_action.py` invocation**: `log_action.py` is at `scripts/openclaw/agents/felix-admin-capture/log_action.py` on Mac, and `/home/claude/kg-automation/scripts/openclaw/agents/felix-admin-capture/log_action.py` on office2. Build the command using `subprocess.run` with the path resolved via:

```python
LOG_ACTION = Path(__file__).resolve().parent.parent / "openclaw/agents/felix-admin-capture/log_action.py"
```

Or use a `LOG_ACTION_PATH` env var override for tests.

**Files**:
- `scripts/inbox/handle_parse_failures.py` (new, ~80–110 lines)

**Validation**:
- [ ] `python3 scripts/inbox/handle_parse_failures.py @/dev/stdin <<<'{"parse_failures": []}'` exits 0 with no stderr.
- [ ] Module is importable as `inject_parse_error_marker` would be (same import-style as existing scripts).
- [ ] Subprocess call to `log_action.py` does not crash when no log_action.py is at the resolved path (in tests, override via env or mock).

**Edge cases**:
- Missing `parse_failures` key in JSON → treat as empty list, exit 0.
- Entry missing `path` key → log error for that entry, increment failure counter, continue.
- `log_action.py` subprocess returns non-zero → log to stderr but do NOT increment the work-item failure counter; logging-infra failure is operationally separate from work-item failure.

### T002 — Create `scripts/inbox/handle_marker_cleanup.py` [P]

**Purpose**: Single helper that does Step 5a end-to-end — strip parse-error markers from every `marker_cleanup_needed` entry.

**CLI**:

```
python3 handle_marker_cleanup.py @/path/to/prescan.json
```

**Steps**:

1. Argument parsing: same `@<path>` convention as T001. No `--date` arg.
2. From the parsed JSON, extract `marker_cleanup_needed` (default `[]`).
3. If empty: exit 0 immediately, emit nothing.
4. Otherwise, for each entry:
   - Call `strip_parse_error_marker.strip_marker(Path(entry["path"]))`.
   - On success: `log_action.py --action marker_stripped --context '{"source_file": "<path>", "issue_number": <entry.issue_number or null>}'`.
   - On failure (raise): `log_action.py --action marker_cleanup_error --context '{"source_file": "<path>", "error": "<str(exc)>"}'`; increment failure counter; continue.
5. Exit 0 if all strips succeeded, else 1 with stderr summary.

**Imports**:

```python
from strip_parse_error_marker import strip_marker
```

**Files**:
- `scripts/inbox/handle_marker_cleanup.py` (new, ~60–80 lines — simpler than T001 because no issue-filing branch)

**Validation**:
- [ ] Exit 0 on empty list.
- [ ] Strip operations log `marker_stripped` action.

### T003 — Create `tests/inbox/test_handle_parse_failures.py` [P]

**Purpose**: Unit-test `handle_parse_failures.py` end-to-end via `subprocess.run`, with mocks for the wrapped library functions and `log_action.py`.

**Approach**: Use `pytest.MonkeyPatch` to set a `HANDLE_PARSE_FAILURES_TEST_MODE=1` env var (or similar) that causes the helper to use stubbed imports. Or — simpler — use `pytest`'s tmp_path + writing a real `log_action.py` stub script to a tmp dir + injecting `LOG_ACTION_PATH` env override to point the helper at the stub. Pick the cleaner option after reading the existing test patterns in `tests/inbox/`.

Alternative: have the helper accept a `--log-action-bin <path>` flag (defaulting to the resolved path) so tests can inject a stub. This is the most explicit and easiest to test.

**Test cases**:

1. **`test_empty_parse_failures_exits_zero`**: Write a JSON tempfile `{"parse_failures": []}`. Run helper. Expect: exit 0, empty stderr, no calls to the log-action stub.

2. **`test_single_parse_failure_full_success`**:
   - Set up: one entry pointing to a real `tmp_path/note.md` with valid YAML frontmatter (so `inject_marker` succeeds).
   - Mock `find_existing_open_issue` → None and `file_new_issue` → 123 (use monkeypatch on the imported names).
   - Run helper. Expect: exit 0, stdout shows `123`, log-action stub was called twice (`inbox_quality_issue_filed` + `parse_error_marker_injected`), the note file now has the marker injected.

3. **`test_dedup_hit`**:
   - Set up: one entry. Mock `find_existing_open_issue` → 99.
   - Run helper. Expect: exit 0, stdout shows `99`, log-action calls include `inbox_quality_issue_deduped` (NOT `_filed`), `file_new_issue` was NOT called.

4. **`test_partial_failure_exits_nonzero`**:
   - Three entries. Mock `inject_marker` to succeed for entries 1 & 3 and raise for entry 2.
   - Run helper. Expect: exit 1, stderr contains entry 2's path, log-action stub called with `parse_failure_handling_error` for entry 2 and `parse_error_marker_injected` for entries 1 & 3.

5. **`test_stdout_emits_issue_number`**:
   - Single-entry happy path. Capture stdout via `subprocess.run(..., capture_output=True)`.
   - Expect: stdout strip equals the integer issue number, no other content.
