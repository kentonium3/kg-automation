# Contract: capture → Felix main delegation payload (calendar create)

**Mission**: `inbox-calendar-and-aspiration-routing-01KTHHXS`
**Spec FR**: FR-005 | **Data model**: [`CalendarEventPayload`](../data-model.md#entity-calendareventpayload-transient-capture--felix-main)

## Purpose

Defines the structured payload capture sends to Felix main when a complete calendar event is ready to write. Mirrors the existing capture → felix-admin-tasker `enrich_task` delegation pattern documented in capture's AGENTS.md (lines ~625–660 of the current AGENTS.md).

## Invocation (from capture's prompt)

```bash
openclaw agent --agent main \
  --message '<JSON payload below>' \
  --json --timeout 120
```

## Payload schema (JSON)

```json
{
  "action": "create_calendar_event",
  "calendar_id": "primary",
  "account": "kent@intentional.biz",
  "summary": "Tuesday trivia night",
  "start_rfc3339": "2026-06-09T18:00:00-04:00",
  "end_rfc3339": "2026-06-09T21:00:00-04:00",
  "start_timezone": "America/New_York",
  "location": "Tru West Brewery, 525 Massachusetts Ave, Acton, MA 01720",
  "description": "Source: Inbox 2026-05-18 1631.md",
  "rrule": "RRULE:FREQ=WEEKLY;BYDAY=TU",
  "attendees": null,
  "source_inbox_path": "/home/kgale/second-brain/notes/01-Inbox/Inbox 2026-05-18 1631.md",
  "clarification_id": null
}
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `action` | string | yes | Always `"create_calendar_event"` for this contract. Distinct from `"resolve_calendar_clarification"` (see Felix main reply handler below). |
| `calendar_id` | string | yes | `"primary"` for v1; future may carry a specific GCal ID. |
| `account` | string | yes | Default `"kent@intentional.biz"`. |
| `summary` | string | yes | Event title. |
| `start_rfc3339` | string | yes | RFC 3339 with offset. |
| `end_rfc3339` | string | yes | RFC 3339 with offset. start < end strictly. |
| `start_timezone` | string\|null | optional | IANA TZ. |
| `location` | string\|null | optional | |
| `description` | string\|null | optional | Auto-generated by capture. |
| `rrule` | string\|null | optional | RFC 5545 RRULE. Null for one-off. |
| `attendees` | string[]\|null | optional | |
| `source_inbox_path` | string | yes | For audit logging. |
| `clarification_id` | string\|null | optional | Always null on first dispatch. Felix main's reply-handler dispatch (see below) sets this when resolving a pending clarification. |

## Felix main response schema (returned via openclaw agent --json)

### Success

```json
{
  "status": "created",
  "gcal_event_id": "abc123xyz",
  "html_link": "https://www.google.com/calendar/event?eid=...",
  "summary": "Tuesday trivia night",
  "start_rfc3339": "2026-06-09T18:00:00-04:00",
  "rrule": "RRULE:FREQ=WEEKLY;BYDAY=TU"
}
```

### Failure

```json
{
  "status": "error",
  "error": "<gog error text, verbatim>",
  "exit_code": <int>
}
```

## Felix main standing-orders delta (new section)

Felix main's workspace AGENTS.md gains a section: "Calendar event creation (delegated)". Pseudocode:

```
When you receive an openclaw agent message with action="create_calendar_event":
1. Parse the payload JSON.
2. Compose the gog command:
   gog calendar create <calendar_id> \
     --account <account> \
     --summary <summary> \
     --from <start_rfc3339> --to <end_rfc3339> \
     [--start-timezone <start_timezone>] \
     [--location <location>] \
     [--description <description>] \
     [--rrule <rrule>] \
     [--attendees <comma-joined>] \
     -j
3. Run it via the exec tool.
4. Parse the gog JSON output:
   - Success → return {"status": "created", "gcal_event_id": <id>, "html_link": <link>, ...}
   - Non-zero exit → return {"status": "error", "error": <stderr>, "exit_code": <code>}
5. If clarification_id is non-null in the input payload, also run:
   - Read ~/second-brain/agents/state/pending-calendar-clarifications.jsonl
   - Filter out the line whose clarification_id matches; write back atomically
   - Log calendar_event_clarification_resolved via log_action
6. Log calendar_event_created (or calendar_event_failed) via log_action.
```

## Felix main standing-orders delta — reply handler

A separate section: "Calendar clarification reply handler".

```
On every inbound WhatsApp message:
1. Check ~/second-brain/agents/state/pending-calendar-clarifications.jsonl. If empty, skip this handler.
2. If non-empty, parse the message body. Look for: time references, duration references, location refs, recurrence refs.
3. Match the message to the oldest open PendingClarificationRecord whose missing_fields are addressed by the message content.
4. Build a CalendarEventPayload by merging fields_so_far + the resolved fields from the reply.
5. Re-run validate_calendar_event.py (via stdin/stdout). If still incomplete, send a WhatsApp turn-summary listing the remaining gaps and STOP (record stays open).
6. If complete, dispatch action="create_calendar_event" with the clarification_id set.
7. Felix main consumes its own dispatched payload via the Calendar event creation section above (step 5 removes the record and logs the resolution).
```

## Error handling

- `openclaw agent` timeout (120s default): capture logs `calendar_event_failed` with reason "delegation timeout", flips source note to `status: needs-review`, surfaces in WhatsApp turn-summary.
- Felix main returns `status: "error"`: capture surfaces the error text verbatim, flips source note to `status: needs-review`, does NOT retry within the cron tick.
- Malformed Felix main response: log as `calendar_event_failed` with reason "malformed response", needs-review.

## Why this contract exists

- Without it, capture and Felix main would drift on field names + semantics across iterations.
- A schema-mismatched delegation produces silent partial events (e.g., title without time) or hard errors that look like gog failures.
- The contract is testable: a Felix main standing-orders change can be reviewed against this document for fidelity.
