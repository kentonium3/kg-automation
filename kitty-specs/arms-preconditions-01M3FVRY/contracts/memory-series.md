# Contract: graph-store memory series (C9)

This contract governs the run-level measure registered in rubric §5 third correction @`91e679e6` and §10 C9 @`91e679e6`.

1. **Measure**: the FalkorDB container's cgroup memory charge, read directly from `/sys/fs/cgroup/system.slice/docker-<full-id>.scope/memory.current` (cgroup v2, systemd driver). It includes page cache and retained allocator heap, so it is a high-water mark. It is never read via `docker stats`, and never recorded under an RSS name.
2. **Writer**: runs on the host inside `substrate.run()` for a harness run only, at a 1.0 s target interval, and records the REAL interval in the series header. The container id is resolved once (`docker inspect`). **The writer is observational.** If it cannot start or produces no reading, that failure is recorded, and the run proceeds with the graph-store figure `could_not_check`. It never blocks the runner or refuses a cell.
3. **Generations**: each `substrate.run` writes its own series file, `RUNS_DIR/falkordb-cgroup-<series_id>.jsonl`. It is created exclusively and never truncated or reused; the existing writer's `"w"` open at `sampler.py` ~L420 changes accordingly. Its header binds `series_id`, `container_id` and `interval_s`. The harness records a `series_generation` ledger event with those values before any graph activity.
4. **Run-level figures** are computed at summary and export time from the series files and harness events. Each is either a number or `could_not_check: <reason>`, and is never a guess:
   - **`baseline_mib`**: before the FIRST `build_graph` of a generation, the harness lists the FalkorDB graphs (read-only). It ALWAYS records `graph_store_first_build{ts, series_id, graphs_present}` with the listing's outcome (clarified 2026-09-27, post-plan review #6). If `graphs_present` is true, baseline is `could_not_check: graphs_present`. Otherwise `baseline_mib` is the latest reading at or before that `ts`, no staler than 5 intervals.
   - **`all_resident_mib`**: emitted ONLY when THIS process has itself built all eight questions' graphs successfully in the current generation, with no harness retirement yet (`graph_store_all_resident{ts, series_id, n_graphs: 8}`, `ts` taken after the eighth build succeeded). The figure is the FIRST reading strictly AFTER that `ts` and within 5 intervals of it. A reading held from before the last build finished never counts. On resume, the graphs built in earlier processes do not count toward the eight: all-resident is established only by one process building all eight, and otherwise it is `could_not_check: not_all_resident_in_one_process`.
   - **`peak_mib`**: the maximum over the readings of every generation whose file has a header matching its `series_generation` descriptor, a clean trailer, first and last readings within 5 intervals of its start and close, and no internal gap over 5 intervals. **Coverage is judged against the generation's own start and close, never against export time.** If any generation fails these, `peak_mib` is `could_not_check: coverage`, because a partial series can hide the true peak.
   - The marginal per-graph figure, `(all_resident_mib − baseline_mib) / 8`, is derived only when both figures are numbers from the SAME generation.
   - **Resumed-generation selector (rubric §5 amendment, 2026-09-28; team-lead ruling `20260928T031145496975Z22b5607322`)**: baseline uses the first generation's first-build boundary in ledger order. All-resident uses the first schema-valid all-resident boundary in ledger order, even when that generation yields `could_not_check`; a later numeric event is never substituted. The interval is numeric only when all running generations agree, otherwise `could_not_check: mixed_intervals`. A numeric baseline and all-resident from different generations make the marginal `could_not_check: different_generation`. The report records an ordered `source_series_ids` list for every scalar so this selection is visible rather than inferred.
5. **Freshness is about the SERIES, not the age of the peak sample.** A peak reached early in a well-covered generation is valid. What must hold is the generation's coverage (item 4), not how recent the maximum-valued sample is.
6. **Two sampler roles, two failure modes.** The ceiling guard's LIVE sampler, unreadable at send, refuses the cell: a safety property (before-send.md). The graph-store figure unavailable is `could_not_check` in the report, and **no cell is ever affected**: it is a reported column, about 0.4 % of the ceiling, outside §7.
7. **No per-cell or per-question graph-store figure exists.** The per-attempt graph-store sampler path in the harness (`run_849_harness.py` ~L543, L551, L655) is REMOVED. Per-cell rows carrying any graph-store column are refused.
